The problem

Postmortem action items drift, and the same bug comes back.

Items live in a doc

"Add a test", "check similar code", "update the runbook". Tracked as tickets, deprioritized in the next sprint, quietly dropped.

"We added a test"

Nothing proves that test would have failed on the broken code. A test that always passes guards nothing.

Same mistake, other files

The root-cause pattern is almost always copy-pasted elsewhere, and nobody goes looking.

02
The insight

Prove, don't claim. Bob generates; a deterministic verifier judges.

@ inc-102-bugEXPECT FAIL
$ vitest run regression.test.js
✗ FAIL  failedOn: assertion
  expected 10 to be less than or equal to 4
exit 1 · 1.1 s
@ inc-102-fixEXPECT PASS
$ vitest run regression.test.js
✓ PASS  all assertions hold

exit 0 · 3.2 s

Same test, two throwaway git worktrees. A crash or import error on the bug commit doesn't count. Anti-cheat rejects skipped, assertion-free or self-mocking tests.

03
The solution

One postmortem in, four verified outputs out.

1 · Regression test

Fails on an assertion at the bug commit and passes at the fix commit. Proven both ways.

2 · Variant rule

A Semgrep rule generalized from the root cause. It must match the bug and not the fix, then it scans the whole app.

3 · Variant fixes

Bob fixes every variant the rule finds. The verifier reruns until none are open.

4 · Action-item audit

Every item is marked guarded / partial / unguarded / process-only, with file evidence. No invented code for runbooks.

One incident, end to end · INC-102 (demo postmortem)

A 4-minute gateway blip became a 47-minute outage. Here's how it never happens again.

SEV-1 · 14 Sep · 47 min

Retry storm took down payments

  • ~48,000 req/min from zero-delay retries
  • API key blacklisted for 43 min
  • 1,847 failed checkouts
  • ₹28.4 lakh estimated lost GMV

root cause
withRetry(fn) with no options: infinite attempts, 0 ms backoff

  1. Bob reads the postmortemseed payment.js:19, fix ref, 5 action items
  2. Bob writes the testa fake gateway that fails, then caps itself at 10 calls; assert calls ≤ 4
  3. @ inc-102-bug: ✗ fails on assertionexpected 10 ≤ 4 in 1.1 s: it catches the real bug
  4. @ inc-102-fix: ✓ passesbounded retries with backoff, 3.2 s
  5. Rule withRetry($F) finds 2 moreclients/inventory.js:13 · clients/sms.js:13, the same outage waiting to happen
  6. Bob fixes both, verifier reruns: GUARDED0 open variants · 4 of 4 code action items with evidence
